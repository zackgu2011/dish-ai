### 早期：10 类模型（已被 31 类取代）

| 指标 | 值 |
| --- | --- |
| top-1（val，同域） | 88.03%（最佳 epoch 23） |
| top-5 | 99.54% |
| 训练 | 30 轮跑满，37 分钟 |
| ONNX | 5.9 MB |

**为什么换成 31 类**：10 类只覆盖食堂 10 道菜，太窄。31 类是食堂菜单里**所有完全同名**的菜，
覆盖翻 3 倍，top-1 只掉 4 个点（88.03% → 83.92%），这个交换划算。

### 错误样本（31 类，浏览器实测）

| 真值 | 预测 | 性质 |
| --- | --- | --- |
| 三杯鸡 | 糖醋排骨 (87.3%) | 深色酱汁类混淆 |
| 家常豆腐 | 麻婆豆腐 (41.9%) | 豆腐类混淆 |

和 10 类模型犯的错是同一类——**同类内部混淆**。且错误样本置信度依然很高（87.3%）。
**再次印证：必须 top-3 + 人工确认，绝不能按置信度自动采纳。**

## ⚠️ MPS/Mac 上的训练提速（重要）

实测瓶颈**不是 GPU，是数据 I/O**：

- Ultralytics 在 MPS/Mac 上会把 `workers` **强制降为 0**（传了也没用），数据加载和训练串行，GPU 干等
- 默认 `cache=False`，每轮都从磁盘重读全部图片并解码
- 日志会报 `Slow image access detected (read: 14.3 MB/s)`
- 31 类 23009 张：每轮 **234 秒**，30 轮约 **2 小时**

**正确配置**（已写进 `train_poc.py`，默认生效）：

```python
model.train(
    cache='disk',   # 关键！快 2-3 倍。16GB 内存时 ram 约需 3.5GB（31 类），disk 更稳
    batch=64,       # MPS 上 GPU_mem 才 1.1G，余量很大
    plots=False,    # 少画图表
)
```

命令行：`python train_poc.py --cache disk --batch 64 --data cls_poc31 --name poc31`

**注意**：改这些参数得从头训。对已经跑到一半的训练，等它跑完通常比重训更划算
（重训 30 轮的时间 > 剩余轮数的时间）。

### 置信度不可信的实测证据
错误样本 `红烧牛肉 → 糖醋排骨` 的置信度是 **97.1%**——错得极其自信。
这印证了可行性分析里引用的基准结论（模型在错误预测上置信度反而更高）：
**绝不能按置信度自动采纳，必须人工确认。**

### 两个实现坑
1. Ultralytics 导出的分类 ONNX **输出已经是概率**（和为 1）。前端再做一次 softmax 会把 0.99 压成 0.23，
   置信度显示全错。要先判断 `sum≈1 且全非负` 再决定是否 softmax。
2. onnxruntime-web 需要指定 `ort.env.wasm.wasmPaths` 指向 CDN，否则 wasm 加载失败。

## 混淆危害分析（比 top-1 更有用的视角）

跑 `analyze_confusion.py`（val 每类抽 40 张）得出的结论：**认错时平均只偏 44 kcal**。

因为大部分混淆发生在热量相近的同类菜之间：

| 混淆 | 热量 | 差 |
| --- | --- | --- |
| 家常豆腐 → 麻婆豆腐 | 115 → 115 | **0** |
| 三杯鸡 → 黄焖鸡 | 202 → 186 | 16 |
| 杭椒牛柳 → 农家小炒肉 | 185 → 212 | 27 |
| 啤酒鸭 → 三杯鸡 | 240 → 202 | 38 |

**真正坑的只有一种：低热量菜被认成深色酱汁肉菜**

| 混淆 | 热量差 |
| --- | --- |
| 酸辣汤(36) → 糖醋排骨(316) | **280** |
| 炒青菜(44) → 糖醋排骨(316) | **272** |
| 卤蛋(75) → 糖醋排骨(316) | **241** |
| 炒青菜(44) → 红烧狮子头(270) | **226** |

错误率最高的菜：炒青菜 55%、红烧牛肉 51%、香菇青菜 42%、三杯鸡 40%、啤酒鸭 38%
—— **绿叶菜和深色酱汁肉**是重灾区。

### 结论：不要为了 top-1 剔掉易混淆的菜

剔掉「麻婆豆腐」能让数字好看，但用户该吃 115 kcal 还是 115，
**一个真问题都没解决，反而少认一道菜**。

正确做法是**在 UI 上预警**：当 top-1 与候选项的热量差 >100 kcal 时提示用户确认。
这比继续卷 top-1 划算得多。

## ⚠️ 83.92% 不能直接当结论

val 与训练集**同分布**（都是网络美食图：精致摆盘、专业打光、白瓷盘）。
食堂实拍是不锈钢餐格 + 顶灯 + 一勺份量，**域差异很大**，真实准确率一定低于 88%。

真正决定「能不能用」的是**食堂实拍图上的 top-1**。下一步必须补实拍测试集（每道菜 10–20 张随手拍即可），
用同一个 best.onnx 跑一遍，看掉多少：

- 掉到 **70% 以上** → 可用，靠 top-3 + 人工确认兜住
- 掉到 **50–70%** → 需要采几百张实拍图做微调
- 掉到 **50% 以下** → 说明网络美食图帮不上忙，得完全靠自建数据
